You are working on a React 19 + TypeScript + Tailwind CSS + Framer Motion + i18next portfolio 
project that already has two portfolios (Dev and Marketing) toggled via a horizontal slide switch.

## Goal
Replace static section-by-section scrolling with a continuous 3D scrollytelling experience using 
React Three Fiber (recommended stack — you may justify an alternative if there's a strong reason, 
but R3F + drei + GSAP ScrollTrigger is the expected default for this kind of camera-driven 
narrative scroll). One persistent 3D scene exists per portfolio; as the user scrolls, the camera 
moves through the scene and the scene transforms/reveals itself in sync with section content.

## Scroll behavior (critical — implement exactly this)
- Hybrid scroll: free/native scroll WITHIN a section's content, but section-to-section transitions 
  SNAP (the page locks to the next/previous section boundary once scroll crosses a threshold, 
  e.g. using a snap-scroll container or a scroll-progress-driven state machine).
- Use scroll position (not scroll-jacking the wheel event entirely) to drive a normalized 
  progress value (0 to 1 per section, or 0 to N across the whole page) that controls camera 
  position/rotation and 3D object states via GSAP ScrollTrigger or a custom scroll-progress hook.
- Section transitions must feel intentional: camera "arrives" at a vantage point for each section, 
  pauses while the user reads/scrolls within that section's content, then moves to the next 
  vantage point when the snap threshold is crossed.

## Content/3D integration
- Content and 3D scene are NOT separate layers — text and UI elements can appear positioned 
  "within" the 3D space (e.g. using drei's `<Html>` component anchored to 3D coordinates, or 
  CSS 3D transforms synced to camera matrix) so that the camera move feels like it's revealing 
  content embedded in the scene, not just scrolling text over a background.
- Some sections may still use simpler overlay text where that makes more sense (use judgment), 
  but the dominant pattern should be content-in-scene with camera-guided reveal.

## DEV portfolio — 3D concept: Motherboard / Circuit Board
- Central metaphor: an illuminated motherboard/PCB that the camera travels across.
- As each section becomes active, a relevant "circuit path" or "chip" lights up / traces with an 
  emissive glow (use emissive materials + bloom post-processing via drei's `<EffectComposer>` 
  /`<Bloom>` for the glow effect).
- Suggested section-to-component mapping (adjust to actual dev portfolio sections):
  - Hero → wide establishing shot of the full board, powering on (boot-up glow animation, nice 
    callback to the existing boot screen intro)
  - About → camera moves to a "CPU" chip area, traces light up
  - Skills/Tech Stack → multiple chips/components light up in sequence as skills are listed, each

  - Projects → camera travels along a main circuit "highway" with branch points representing each 
    project; could use glowing nodes the user can see content pop out of
  - Contact → camera arrives at an "I/O port" or connector at the edge of the board
- Color language: keep emissive glow in Sky Blue (#0ea5e9) / Violet (#7c3aed) to match existing 
  dev brand, board surface in dark green/black (classic PCB look) blended with the existing 
  Slate 900/800 dark theme.

## Performance strategy (middle-ground approach — implement all of these)
- Detect device capability on mount: check `navigator.hardwareConcurrency`, screen width 
  (mobile breakpoint), and ideally a quick WebGL capability/renderer check.
- Provide a "lite mode" fallback for mobile/low-power devices:
  - Reduce particle counts / geometry complexity significantly
  - Disable or simplify post-processing (no bloom, or a cheaper glow technique)
  - Lower pixel ratio (`gl={{ pixelRatio: Math.min(devicePixelRatio, 1.5) }}` or similar)
  - Consider replacing full camera-fly-through with simpler per-section static 3D backgrounds on 
    very low-end devices (graceful degradation, not feature parity)
- Respect `prefers-reduced-motion`: disable camera movement animation, snap instantly between 
  section states, keep the 3D scene visually present but static.
- Lazy-load the Three.js/R3F bundle (dynamic import) so it doesn't block initial page load — 
  show existing boot screen / a lightweight loading state while the 3D scene initializes.
- Dispose of Three.js resources properly on unmount (geometries, materials, textures) to avoid 
  memory leaks, especially relevant since users can toggle between Dev/Marketing portfolios 
  (which should fully unmount the inactive scene, not keep both WebGL contexts alive 
  simultaneously — only one canvas should be active at a time).

## Suggested architecture
- `src/three/dev/DevScene.tsx` — the motherboard scene, camera rig, lighting, post-processing
- `src/three/marketing/MarketingScene.tsx` — the marketing concept scene
- `src/three/shared/ScrollProgressProvider.tsx` — context/hook exposing normalized scroll 
  progress (per-section and global) to both the 3D scene and the HTML content layer
- `src/three/shared/useDeviceCapability.ts` — hook returning a lite/full mode flag
- `src/hooks/useScrollSnap.ts` — handles the hybrid free-scroll-then-snap behavior
- Each existing section component (`Hero.tsx`, `About.tsx`, etc.) gets refactored to consume 
  scroll progress and render its content either as a `<Html>`-anchored 3D-positioned block or 
  as a synced overlay, per the content/3D integration approach above
- Wire scene mounting into the existing `PortfolioSwitcher.tsx` so only the active portfolio's 
  Canvas is mounted
